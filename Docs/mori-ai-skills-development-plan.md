# MORI AI 스킬 개발계획서

> 2026-09-09: 공용 로컬 CLI와 `mori-context` 스킬 0.1.0 구현. 검색·읽기·검토된 새 메모 생성 및 설치 방법은 [구현 기록](mori-context-skill.md)을 참고한다. 아래 계약은 최초 설계이며 실제 전송은 로컬 Python CLI, freshness는 코드 검증 전 unknown, 기존 메모 갱신·삭제는 후속 범위다.

> Codex와 Claude가 현재 작업에 필요한 MORI 지식을 찾아 읽도록 만드는 별도 계획서다. MORI 앱의 사용자 기능과 Apple 메모 가져오기는 [MORI 앱 개발계획서](mori-app-development-plan.md)에서 다룬다.

## 목표

Codex·Claude가 저장소 작업을 시작할 때 MORI를 시스템 지식 공간으로 조회하게 한다. MORI는 특정 저장소에 강제 매핑되지 않으며, AI는 현재 열려 있는 저장소와 사용자의 작업 요청을 기준으로 필요한 문서를 검색한다.

## 아이데이션에서 확정한 방향

- MORI는 저장소 관리 앱이 아니라 시스템 구조, 공통 규칙, 기술 결정, 프로젝트 기록을 보관하는 지식 공간이다.
- Codex와 Claude의 스킬은 MORI 앱과 별도 배포·버전·권한 경계를 가진다.
- 작업 시작 시 현재 저장소의 맥락과 사용자의 요청으로 MORI를 검색한다. 사전에 저장소-MORI 프로젝트 연결을 필수로 만들지 않는다.
- MSA 작업에서는 `공통 규칙/시스템 구조 → 서비스 간 관계 → 현재 서비스 문서` 순서로 필요한 문서를 좁혀 읽는다.
- 관련 문서가 없거나 오래됐다고 판단되면 현재 코드를 곧바로 MORI에 저장하지 않고, 먼저 사용자에게 분석·문서 초안 작성을 제안한다.
- 기본 권한은 읽기 전용이다. 문서 생성·갱신·삭제는 사용자가 명시적으로 승인한 요청에서만 수행한다.
- AI가 참고한 MORI 문서의 제목·식별자·간단한 이유를 작업 결과에 표시해 근거를 추적할 수 있게 한다.

## 범위와 경계

### 포함

- Codex용 MORI 검색·읽기 스킬
- Claude용 MORI 검색·읽기 스킬
- 두 클라이언트가 공유하는 검색 결과·문서 읽기·출처 표시 규약
- 현재 작업에서 관련 문서를 찾는 검색 전략
- 문서 부재·신선도 경고와 사용자 승인 흐름
- 읽기 기본값과 쓰기 승인 경계

### 제외

- MORI의 Apple 메모 가져오기, 편집기, 폴더 UI
- 특정 저장소를 MORI에 영구 연결하는 설정
- AI가 사용자의 승인 없이 MORI 문서를 쓰거나 수정하는 동작
- AI가 MORI 전체 문서를 무차별적으로 컨텍스트에 넣는 동작
- 모델·API 제공자 자체의 인증과 과금 정책

## 에이전트 작업 흐름

1. AI가 사용자 요청과 현재 저장소의 루트·언어·프레임워크·변경 대상 파일을 파악한다.
2. MORI 검색어를 작업명, 도메인 용어, 서비스명, 오류명, 파일 경로에서 만든다.
3. 공통 컨벤션과 시스템 구조를 먼저 검색하고, 결과에서 현재 서비스·모듈로 범위를 좁힌다.
4. 검색 결과의 제목·요약·신선도만 먼저 읽은 뒤 실제 작업에 필요한 원문만 추가로 요청한다.
5. 문서가 충분하면 그 내용을 개발 판단에 반영하고, 참고한 문서 목록을 내부 작업 기록과 최종 결과에 남긴다.
6. 문서가 없거나 코드와 불일치할 가능성이 있으면 사용자에게 “현재 코드 분석 후 MORI 문서 초안을 만들지” 묻는다.
7. 사용자가 승인한 경우에만 초안을 MORI에 저장한다. 저장 전 대상 문서, 변경 요약, 출처 파일을 보여준다.

## 공유 인터페이스

구체적인 MCP/CLI 전송 방식은 Codex와 Claude의 실행 환경을 확인한 뒤 정하지만, 두 스킬이 기대하는 논리 인터페이스는 동일하게 유지한다.

```ts
interface MoriSearchRequest {
  query: string;
  scope?: string[];
  limit: number;
  includeStale?: boolean;
}

interface MoriSearchResult {
  documentId: string;
  title: string;
  summary: string;
  scope?: string;
  updatedAt?: string;
  freshness: 'current' | 'stale' | 'unknown';
  relevance: number;
}

interface MoriReadResult {
  documentId: string;
  title: string;
  content: string;
  updatedAt?: string;
  sourceRefs?: string[];
}

interface MoriWriteProposal {
  title: string;
  content: string;
  reason: string;
  sourceRefs: string[];
}
```

스킬은 검색·읽기 결과를 근거 목록으로 누적한다. 최종 응답에는 최소한 `참고한 MORI 문서` 목록과 문서별 사용 이유를 표시한다. 검색 결과가 없었다는 사실도 필요하면 기록한다.

## 문서 신선도와 저장소 관계

MORI 문서가 특정 저장소에 필수로 연결되지는 않는다. 대신 문서 본문이나 메타데이터에 서비스명, 기술, 경로, 결정 시점을 선택적으로 포함하고, AI가 현재 코드와 의미상 일치하는지를 판단한다. 코드가 크게 달라졌거나 문서의 결정 시점이 오래됐으면 `stale` 또는 `unknown`으로 표시한다.

문서가 오래됐다는 판정은 자동 확정이 아니라 사용자에게 확인을 요청하는 신호다. AI는 낡은 문서를 현재 사실처럼 적용하지 않고, 현재 코드에서 확인한 내용과 MORI 문서의 차이를 설명한다.

## Codex·Claude별 개발 범위

### 공통 스킬 규약

- 검색어 구성, 결과 축약, 원문 추가 읽기, 출처 표시, 쓰기 승인 문구를 공유한다.
- MORI 연결이 없어도 현재 저장소 작업은 계속할 수 있어야 한다.
- MORI 장애·인증 실패·검색 결과 없음은 코드 작업 전체를 막지 않고 상태를 보고한다.

### Codex 스킬

- Codex의 스킬/명령 형식에 맞춰 MORI 검색과 읽기를 호출한다.
- 현재 Codex 세션의 저장소 경로와 변경 대상 파일을 검색 맥락으로 제공한다.
- 문서 쓰기는 명시적 사용자 승인 단계에서만 실행한다.

### Claude 스킬

- Claude의 스킬 형식에 맞춰 같은 논리 인터페이스를 제공한다.
- Claude Code의 현재 작업 디렉터리와 파일 맥락을 검색 맥락으로 사용한다.
- Codex와 동일한 출처 목록 형식과 승인 문구를 사용해 결과를 비교할 수 있게 한다.

두 구현은 내부 호출 방식이 달라도 사용자에게 보이는 원칙과 데이터 계약은 같아야 한다. 각 클라이언트의 실제 스킬 포맷·도구 권한·설치 위치는 해당 환경을 조사한 뒤 정한다.

## 단계별 개발계획

### 1단계: 지식 조회 계약 확정

- MORI에서 문서 검색·읽기·출처 메타데이터를 제공하는 현재 기능을 확인한다.
- 위 논리 인터페이스를 실제 API/CLI/MCP 중 가능한 경계에 매핑한다.
- 검색 결과 요약과 원문 읽기를 분리한다.
- 읽기 전용 토큰/권한과 쓰기 승인 요청의 표현을 정한다.

완료 조건은 Codex와 Claude가 같은 입력에 대해 같은 의미의 검색·읽기 결과를 받을 수 있는 계약이 문서화되는 것이다.

### 2단계: Codex 스킬 구현

- 작업 맥락 추출, MORI 검색, 결과 선별, 원문 읽기, 출처 누적을 구현한다.
- 문서 없음·stale·MORI 접근 실패 각각에 대한 사용자 안내를 만든다.
- 승인 전에는 어떤 쓰기 호출도 하지 않도록 권한 경계를 확인한다.

### 3단계: Claude 스킬 구현

- Claude 스킬 형식과 설치 경로에 맞춰 동일한 검색·읽기 흐름을 구현한다.
- Codex와 동일한 출처 표시와 문서 신선도 안내를 적용한다.
- 두 클라이언트의 검색 결과·오류·승인 동작을 같은 fixture로 비교한다.

### 4단계: 승인 기반 문서 생성과 운영 검증

- 관련 문서가 없을 때 현재 코드 분석 결과를 문서 초안으로 제안한다.
- 승인 화면/프롬프트에는 대상, 이유, 본문, 출처 파일, 덮어쓸 기존 문서 여부를 포함한다.
- 저장 후 문서 ID와 저장 결과를 AI 응답에 남긴다.
- 실제 MSA 작업에서 공통→관계→서비스 순서가 과도한 문서 읽기를 만들지 않는지 확인한다.

## 오류와 안전

- MORI가 응답하지 않으면 AI는 검색 실패를 숨기지 않고 코드 기준으로 진행할지 사용자에게 알린다.
- 검색 결과가 없다고 문서가 없다고 단정하지 않는다. 검색어를 조정한 한 번의 재검색 후에도 없을 때 제안한다.
- stale 문서는 자동 적용하지 않고 현재 코드 확인과 사용자 확인을 거친다.
- 쓰기 요청은 문서 초안과 변경 diff를 먼저 보여주며, 승인 없는 저장·삭제·덮어쓰기를 금지한다.
- 민감한 코드나 비밀값을 MORI에 저장할 때는 출처와 대상 내용을 사용자에게 표시하고, 기본 스킬은 비밀값을 문서화하지 않는다.
- 참고 문서 목록은 AI가 실제로 읽은 문서만 기록한다. 검색 결과 제목만 본 문서는 `검색 후보`로 구분한다.

## 검증 계획

- 검색 단위: 키워드·서비스명·파일 경로 조합, 결과 제한, 요약→원문 2단계, stale 필터
- 계약 테스트: Codex와 Claude adapter가 동일 fixture에서 동일한 논리 결과를 반환
- 권한 테스트: 읽기 호출은 가능, 승인 전 쓰기 호출은 차단, 승인 후에만 저장
- 근거 테스트: 실제 읽은 문서만 결과 목록에 포함, 검색 실패·무결과도 표현
- MSA 시나리오: 공통 규칙과 시스템 관계를 먼저 읽고 현재 서비스 문서를 추가하는지 확인
- 장애 테스트: MORI 미실행, 인증 실패, 네트워크 지연, 잘못된 문서 ID, 오래된 문서

## 후속 아이디어와 우선순위

후속 후보는 작업별 MORI 참고 기록, 문서 간 모순 감지, 코드 변경으로 인한 신선도 후보 자동 제안, 사용자가 지정한 지식 범위, 로컬 임베딩 검색이다. 임베딩과 자동 문서 갱신은 검색 품질과 승인 경계를 검증한 후 별도 결정한다.

## 열린 질문

- 현재 MORI가 제공할 수 있는 검색·읽기 경계는 로컬 CLI, MCP, HTTP 중 무엇이 가장 안정적인가?
- 문서 신선도를 판단할 코드 기준(경로, 커밋, 서비스 버전)을 어느 정도까지 저장할 것인가?
- 출처 목록을 최종 답변에 항상 노출할지, 작업 로그와 사용자 답변을 분리할지?
- 문서 초안 승인 UI는 MORI 앱에서 할지, Codex·Claude 대화 안에서 할지?
