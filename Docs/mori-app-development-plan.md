# MORI 앱 개발계획서

> MORI 자체를 개발하기 위한 계획서다. Codex·Claude가 MORI를 읽는 방식은 [MORI AI 스킬 개발계획서](mori-ai-skills-development-plan.md)에서 별도로 다룬다.

## 목표

MORI를 개인 지식 위키로 발전시키고, Apple 메모의 내용을 MORI로 안전하게 가져오는 macOS 기능을 제공한다. Apple 메모는 입력 원본이고 MORI는 사용자가 정리·검색·연결하는 작업 공간이다.

## 아이데이션에서 확정한 방향

초기 아이디어를 검토한 결과 다음을 제품 원칙으로 확정한다.

- Apple 메모에서 MORI로의 **단방향 가져오기**만 지원한다. MORI에서 Apple 원본을 수정하거나 Apple 메모로 되돌려 쓰지 않는다.
- 동기화라는 표현을 쓰더라도 실제 동작은 MORI가 Apple 메모의 최신 내용을 다시 읽어오는 가져오기다. 양방향 편집 동기화는 범위에서 제외한다.
- 사용자는 실행할 때 `연결된 모든 항목` 또는 `직접 선택`을 고른다. 폴더 전체와 개별 메모를 선택할 수 있어야 한다.
- 가져온 문서에는 원본 식별자, 원본 제목·폴더, 가져온 시각, 마지막 확인 시각을 남긴다. MORI에서 만든 문서와 출처를 구분할 수 있어야 한다.
- Apple 원본과 MORI 사본이 모두 바뀐 경우 자동 덮어쓰기나 자동 병합을 하지 않고 검토 보관함에 넣는다.
- MORI는 저장소와 강제로 연결되는 프로젝트 관리 도구가 아니다. 저장소 연결, Git 상태 수집, 저장소별 지식 자동 매핑은 이 앱 계획서의 범위가 아니다.
- 첨부파일·스캔·복잡한 Apple 전용 서식은 지원 가능성을 조사한 뒤 지원 범위를 명시한다. 확인하지 않은 Apple 비공개 API나 동작을 전제로 설계하지 않는다.

## 범위와 경계

### 포함

- Apple 메모 가져오기 시작·대상 선택·결과 확인 UI
- 원본 provenance와 마지막 가져오기 상태 표시
- 새 문서 생성, 기존 문서 갱신, 변경 없음 처리
- 양쪽 변경 시 검토 보관함과 원본/사본 비교
- 기존 Markdown·문서 ID·폴더·링크 모델과의 호환
- 가져오기 실패 항목 재시도와 오류 로그

### 제외

- Apple 메모 원본 수정, 삭제, 이동, 이름 변경
- Apple 메모와 MORI 사이의 양방향 실시간 동기화
- iPhone/iPad 앱과 CloudKit 동기화
- 비공개 Apple API에 의존한 첨부파일·서식 완전 복제
- 자동으로 특정 Git 저장소를 MORI 프로젝트에 연결하는 기능
- AI 검색·프롬프트·Codex/Claude 호출 규약. 해당 내용은 [AI 스킬 계획서](mori-ai-skills-development-plan.md)에서 관리한다.

## 사용자 흐름

1. 사용자가 MORI에서 `Apple 메모 가져오기`를 선택한다.
2. MORI가 접근 가능 여부와 현재 연결된 가져오기 항목을 보여준다.
3. 사용자가 `연결된 모든 항목` 또는 `직접 선택`을 고른다.
4. 직접 선택이면 Apple 메모의 폴더와 메모 목록에서 대상을 고른다.
5. 실행 전 예상 결과를 `새 문서`, `변경 문서`, `검토 필요`, `변경 없음`으로 미리 보여준다.
6. 사용자가 실행한다. 원본은 읽기만 하고 MORI 사본만 기록한다.
7. 결과 화면에서 성공·실패·검토 필요 항목을 확인하고, 검토 항목은 비교 화면에서 처리한다.
8. 각 MORI 문서의 출처 패널에서 Apple 원본 제목, 위치, 마지막 확인 시각을 본다.

## 데이터와 동작

가져오기 메타데이터는 본문과 분리된 문서 메타데이터로 보관한다. 구현 시 기존 저장 구조와 충돌하지 않는 위치를 선택한다.

```ts
type ImportSource = 'apple-notes';

interface ImportProvenance {
  source: ImportSource;
  sourceId: string;
  sourceTitle: string;
  sourceFolder?: string;
  importedAt: string;
  lastSeenAt: string;
  sourceContentHash: string;
  importedContentHash: string;
}

type ImportOutcome = 'created' | 'updated' | 'unchanged' | 'review' | 'failed';
```

- `sourceId`는 Apple 쪽에서 안정적으로 얻을 수 있는 식별자만 사용한다. 안정적 식별자를 얻을 수 없는 경로에서는 가져오기 시점의 명시적 매핑을 저장하고 한계를 사용자에게 표시한다.
- MORI 문서의 수정 시각과 `importedContentHash`를 비교해 MORI 사본 변경을 감지한다.
- Apple에서 읽은 최신 내용의 해시와 `sourceContentHash`를 비교해 원본 변경을 감지한다.
- 원본만 변경되면 사용자가 선택한 정책에 따라 MORI 사본을 갱신하되, 이전 MORI 버전은 기존 revision history에 남긴다.
- MORI만 변경되면 원본을 건드리지 않고 가져오기 결과를 `unchanged` 또는 사용자 확인 대상으로 처리한다. 초기 구현에서는 덮어쓰기를 막고 검토 대상으로 분류한다.
- 양쪽이 변경되면 `review`로 만들고 두 내용을 나란히 보여준다. 사용자는 MORI 사본 유지, Apple 최신 내용으로 새 버전 생성, 두 내용을 수동 편집해 저장 중 하나를 선택한다.

Apple 접근 구현은 먼저 현재 macOS에서 사용할 수 있는 **문서화된 접근 경계**를 검증한다. EventKit, AppleScript/JXA, Shortcuts, 내보내기 파일 등 실제로 사용 가능한 경로를 조사하고, 권한·식별자·본문/체크리스트/첨부파일 지원을 확인한 뒤 어댑터를 고른다. 비공개 데이터베이스 직접 읽기나 존재가 확인되지 않은 API를 계획의 전제로 삼지 않는다.

## 단계별 개발계획

### 1단계: 가져오기 경계와 기존 저장 모델 확인

- 기존 문서 ID, Markdown, revision, trash, folder 모델을 정리한다.
- Apple 메모 접근 후보를 작은 탐색기로 검증한다.
- 접근 권한 거부, 잠긴 메모, 폴더·제목·본문·체크리스트·첨부파일의 실제 반환 형태를 기록한다.
- 지원하지 않는 콘텐츠는 누락시키지 말고 사용자에게 항목별 상태를 보여주는 규칙을 정한다.

완료 조건은 사용할 API/자동화 경계와 지원 범위가 실제 실행 결과로 문서화되는 것이다.

### 2단계: provenance와 가져오기 도메인 구현

- `AppleNotesSourceAdapter`와 내부 표준 `ExternalNote` 모델을 만든다.
- 선택 대상, 전체 대상, 중복 실행을 처리하는 순수 비교 로직을 만든다.
- 메타데이터 원자 저장과 기존 revision history를 재사용한다.
- 실패 항목을 전체 작업 실패와 분리해 재시도할 수 있게 한다.

### 3단계: 사용자 흐름과 검토 보관함

- 가져오기 설정 화면, 대상 선택 화면, 미리보기, 결과 화면을 구현한다.
- 문서 출처 패널과 마지막 확인 시각을 표시한다.
- 충돌 비교 화면과 검토 결과 저장을 구현한다.
- 접근 권한 요청과 실패 원인을 재현 가능한 문구로 안내한다.

### 4단계: 안정화와 후속 확장 판단

- 실제 Apple 메모 데이터로 회귀 테스트를 수행한다.
- 대량 메모, 중복 제목, 빈 메모, 삭제·이동된 원본을 확인한다.
- 첨부파일과 서식은 검증된 범위만 정식 지원으로 올린다.
- 아이폰 동기화나 양방향 동기화는 별도 계획으로 분리한다.

## 오류와 안전

- Apple 접근 권한이 없으면 설정 위치와 재시도 동작을 안내한다.
- 원본을 수정하는 호출은 어댑터 인터페이스에 포함하지 않는다.
- 가져오기 중 앱이 종료돼도 부분 결과가 손상되지 않도록 문서별 원자 저장과 작업 상태를 사용한다.
- 동일 원본이 여러 MORI 문서에 매핑되지 않도록 매핑 충돌을 검토 상태로 표시한다.
- 읽을 수 없는 첨부파일이나 서식은 조용히 버리지 않고 경고와 원본 항목명을 기록한다.
- 삭제된 원본은 MORI 문서를 자동 삭제하지 않는다. 사용자가 출처 상태를 확인한 뒤 직접 처리한다.

## 검증 계획

- 단위: hash/변경 판정, 신규·변경 없음·MORI 변경·양쪽 변경 분류, provenance 직렬화
- 어댑터 계약: 정상 메모, 폴더, 빈 본문, 특수문자, 권한 거부, 접근 실패, 지원하지 않는 첨부파일
- 통합: 전체 선택과 직접 선택, 재실행 idempotency, 중간 실패 후 재시도, 문서 ID·링크 보존
- UI 수동 검증: 미리보기 수량과 실제 결과 일치, 검토 비교, 출처 표시, 오류 메시지
- 회귀: 기존 Markdown 편집·폴더·revision·trash·검색 기능이 가져오기 추가 후 동일하게 동작

## 후속 아이디어와 우선순위

후속 후보는 원본별 가져오기 프로필, 지원 콘텐츠 진단 리포트, 충돌 양쪽 버전 나란히 보기 개선, 가져오기 예약 알림, Apple 메모 내보내기 파일 보관이다. 이 항목들은 단방향 가져오기의 신뢰성과 기본 UX가 검증된 뒤 우선순위를 다시 정한다.

## 열린 질문

- 현재 macOS 환경에서 권한 요청과 데이터 접근에 가장 안정적인 문서화 경계는 무엇인가?
- Apple 메모의 체크리스트·표·첨부파일 중 1차 릴리스에서 보존할 범위는 어디까지인가?
- MORI만 변경된 문서를 항상 검토로 보낼지, 사용자가 “가져오기 시 새 버전 추가” 정책을 선택하게 할지?
- 동일 원본을 여러 번 가져올 때 제목 변경과 폴더 이동을 어떤 UI로 확인하게 할지?
